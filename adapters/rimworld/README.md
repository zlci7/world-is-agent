# WIA RimWorld Adapter

Connects RimWorld to a local [World Is Agent](../../README.md) Runtime.

```text
Requires      WIA Protocol v1alpha2
Tested against protocol-v1alpha2.0
Game          RimWorld 1.6 (built and tested against 1.6.4871)
Platform      Windows x64 — Unity 2022.3.35f1, Mono 6.13
```

This is the second real adapter for WIA. Its scope is **dialogue only**: a colonist can talk to the
player, and the reply is generated by the Runtime's normal event → observation → context → model →
capability chain. It does not move pawns, take over RimWorld's AI, or react to world events on its
own.

The whole path runs: the gizmo sends `player_interacted_with_npc`, the adapter answers
`ObserveRequest` with bounded state, the model's `present_dialogue` call opens the window, and the
player's reply sends `player_said_to_npc`. It has been exercised end to end in game with three
colonists; see [Status](#status).

## Requirements

- **Windows x64.** The adapter targets .NET Framework 4.7.2, loads `Grpc.Core`'s native library
  through `kernel32!LoadLibraryW`, and ships only `grpc_csharp_ext.x64.dll`. Linux and macOS are not
  supported.
- RimWorld 1.6. The adapter compiles against reference assemblies, so a game install is needed only
  to run it, never to build it.
- The vanilla `Human` def, unchanged in the way that matters: the WIA entry point is an XML patch
  on `Human`'s comps, so a mod that rewrites that def can remove the gizmo.
- A WIA Runtime listening on `127.0.0.1:50051`, with **RimWorld** selected and Ready. Choose the game
  in the Runtime console; that prepares the Runtime-owned profile under `runtime/config/games/rimworld`.
  The Runtime can be started before or after the game. The address is fixed in the
  adapter — there is no settings entry yet — so running the Runtime on a different `--grpc-addr`
  requires rebuilding the adapter with that address.

## Build

No game installation is required. The project compiles against reference assemblies published with
Ludeon's permission (`Krafs.Rimworld.Ref`), so no game binary is redistributed and CI needs no game.

```powershell
dotnet build WiaRimWorld.csproj
```

The protocol is located through `WIA_PROTOCOL_DIR`, with a repository-relative fallback for local
development:

```powershell
dotnet build WiaRimWorld.csproj -p:WIA_PROTOCOL_DIR=<path to protocol>
```

To verify that the adapter builds with no game and outside the repository layout:

```powershell
adapters/rimworld/tests/check-standalone-build.ps1
```

### Tests

The parts of the adapter that do not touch RimWorld are covered by tests that run without the game:

```powershell
dotnet test adapters/rimworld/tests/Projection.Tests/WiaRimWorld.Projection.Tests.csproj
```

The test project links the projection and dialogue sources rather than referencing the adapter
assembly. That is deliberate: the build fails the day one of those files starts depending on
RimWorld, which is the property that keeps them testable off-line. Reading a pawn and drawing a
window stay outside that boundary, so they are verified in game instead.

## Install

```powershell
scripts/install-rimworld-adapter.ps1 -GamePath "<RimWorld install>"
```

The game path can also come from `WIA_RIMWORLD_GAME_PATH`. Then enable **World Is Agent (RimWorld)**
in RimWorld's mod list.

The installed layout is not a plain copy of the build output:

```text
<Game>\Mods\WiaRimWorld\
  About\About.xml
  Assemblies\   WiaRimWorld.dll + its managed dependencies
  Native\       grpc_csharp_ext.dll
  Patches\      WiaEntryPoint.xml
```

Four rules are enforced by the install script because RimWorld's loader requires them:

1. **The native library must not live in `Assemblies/`.** RimWorld hands every `*.dll` in that folder
   to `Assembly.LoadFrom`; a native image throws `BadImageFormatException`, and because managed
   assemblies load in filename order, that failure can stop the adapter assembly from loading at all.
   The symptom is a game that runs normally with a silently inactive mod.
2. **The native library must be named exactly `grpc_csharp_ext.dll`.** That is the name
   `Grpc.Core`'s `DllImport` asks for; Windows `LoadLibrary` does not match an already-loaded module
   by a different base name. The adapter pre-loads it by absolute path at startup.
3. **Staging is a whitelist, not a merge.** `Assemblies/`, `Native/` and `Patches/` are emptied
   before the current build is copied in, so nothing a previous version installed can survive an
   upgrade. RimWorld loads every `*.dll` in `Assemblies/`, so a stale dependency is not clutter — it
   is part of what runs. A leftover patch XML would keep modifying defs after the code that relied on
   it is gone.
4. **The game must not be running.** RimWorld holds the staged assemblies open, and the script
   refuses rather than emptying a folder it cannot refill.

## Using it in game

Select a colonist; a **WIA 对话** gizmo appears in the command bar. Clicking it starts a conversation
with the Runtime: the colonist's line appears in a window with three replies, plus a text field when
the model allows free text. Closing the window without replying simply ends that conversation — no
reply is sent and nothing is left pending.

The gizmo is disabled, with the reason shown, while the Runtime is not connected. It appears only on
eligible colonists: vanilla `Human`, player faction, alive, and not a prisoner, guest or slave.

## Failure behaviour

None of these is silent in the log:

| Failure | Behaviour |
| --- | --- |
| `Native/grpc_csharp_ext.dll` is missing or cannot be loaded | The adapter logs `adapter disabled, no connection will be attempted` with the reason, creates no pump and **never opens a connection**. Retrying cannot fix a missing file, so this is reported as an installation error instead of an endless connect loop. The check runs once, in the mod's static constructor: staging the file afterwards does not recover the running game, RimWorld has to be restarted. |
| The Runtime is not running, or shuts down | The adapter logs the failed connection and retries every 5 seconds. Starting the Runtime later connects without restarting the game. |
| The Runtime is not Ready | The Runtime rejects the stream with `runtime_not_ready`; the adapter retries every 5 seconds and connects after setup completes. |
| The Runtime loaded another game | The Runtime rejects the stream with `game_mismatch` before environment readiness or capability discovery. Choose RimWorld and restart the Runtime if it is shown as Next Game. |
| An observation cannot be read | The adapter answers the `ObserveRequest` with a correlated error naming the reason, rather than an empty observation. A fabricated state would be indistinguishable from a real one. |
| The player clicks the gizmo while not connected | A message says so. A click that silently produces nothing is indistinguishable from a broken mod. |

## Transport

The adapter talks to the Runtime with `Grpc.Core` (the native C-core implementation) over an
unencrypted loopback HTTP/2 stream.

This is not a preference. RimWorld runs on Unity's Mono, whose BCL has no HTTP/2 implementation:
`System.Net.Http.SocketsHttpHandler` does not exist and the assembly contains no HTTP/2 identifiers
at all. `grpc-dotnet` therefore cannot work in this process, and gRPC-Web is not an option because
the adapter protocol is a single bidirectional stream. `Grpc.Core` bypasses the BCL HTTP stack
entirely, at the cost of carrying a native library and depending on an upstream that is in
maintenance mode. That debt belongs to this adapter, not to the Runtime or the protocol.

## Status

The dialogue path was verified in game as a dated Phase 10.3 baseline. Three colonists across two sessions were spoken to: each gizmo click
produced exactly one turn, the model chose `present_dialogue` every time, the window appeared with
the colonist's line and three replies, and each reply produced exactly one further turn. Closing the
window produced none. The Runtime admits the capability with `accepted=1 catalog=1` and no warnings,
and the off-line suite covers the projection's bounds and determinism and both legal dialogue forms
with their rejections.

Phase 10.4 Game Profile selection and switching still require user acceptance with the real game; the Phase 10.3 observations above do not establish that newer acceptance result.

Known gaps, stated so they are not mistaken for coverage: the isolation between two colonists is
evidenced at the level of turns, history sources and per-entity memory accounting, not by a
field-by-field context dump; and a colonist's line reflects their own projected traits and skills,
which is qualitative rather than a proof. Nothing here has been tested against a colony holding
prisoners or raiders, so the claim that the gizmo stays off them rests on the eligibility check in
`WiaDialogueComp`, not on an observation.
