## 1. 产品目标与技术原则

面向普通玩家交付功能完善、默认可用、低配置门槛的 AI 叙事角色扮演应用。用户通过自然语言游玩，系统自动完成场景协调、NPC 决策、信息分发、记忆使用、回顾和建议。

| 产品目标 | 技术责任 |
| --- | --- |
| 直接开始故事 | 可玩示例、主角默认值、模型连接引导、可验证的预设配置 |
| 自然的多人互动 | 场景主 Agent 与在场重要 NPC Agent 协作，统一输出完整叙事 |
| 世界有剧情，玩家有选择 | 开放型与流程型共用运行架构，按游戏内时间和条件推进世界剧情 |
| 人物有自己的经历 | 稳定身份、独立可见上下文、持续记忆、关系判断与关切 |
| 人物知道不同的事情 | 事件与各人的感知记录分离，所有上下文入口执行同一信息范围 |
| 长期游玩可延续 | 自动整理、受控检索、近期尾部完整覆盖、当前世界持续持久化 |
| 进度可保存与接续 | 当前进度另存为独立世界数据库，读取后持续更新该世界 |
| 出错可修正 | 有来源的记录、明确的纠正对象、统一失效与可恢复重建 |
| 普通玩家用得到功能 | 默认启用，自动触发；技术策略留在内部，辅助能力按需关闭 |

不以 token 成本压缩角色能力或规定固定的少量总调用。执行期限、上下文边界和并发限制用于保证工作能够结束、服务稳定及数据正确。优化顺序是先验证体验和质量，再依据实测做缓存、检索与调度优化。

### 1.1 叙事容错与程序正确性

本产品接受少量不影响持续游玩的模型幻觉，不以百分之百的语义准确作为开发或交付前提。人物理解、感知合理性、旁白措辞与剧情衔接属于体验质量；通过上下文、明确职责、连续游玩评估及纠正入口改进。

程序执行可验证的结构、来源、权限、版本和事务检查。跨人物或跨世界读取错误、写错存档、半轮数据提交、重复执行、凭据暴露等属于实现缺陷，不归入模型容错。模型在合法输入下误解或猜测，与程序直接提供越界数据分别诊断。

正常回合不配置固定的额外裁判 Agent、逐句事实核对或全量语义证明。轻微叙事偏差不自动触发整轮失败和反复重生成；格式或引用错误按有限修复处理，明确的程序约束违规、关键调用失败及存储失败按失败路径处理。必要的追加 NPC 决策由新事件触发，不为检查每句话而固定追加调用。

### 1.2 产品架构边界

本应用以叙事产品自身的需求设计，由故事运行服务管理世界、场景、人物和执行结果。核心架构围绕剧本、世界存档和 NPC 重构，适用的模型接入、身份与执行基础设施按需复用；Adapter 调用链、游戏协议兼容和通用任务框架不构成产品设计约束。

## 2. 总体架构

```text
Windows 桌面 / 本机浏览器 / 服务器上的电脑与手机浏览器
                         │
                  共享叙事 Web UI
                         │
                  AppAPI + AppAuth
                         │
AppHost：生命周期、任务执行池、模型档案、凭据、存储装配
                         │
StoryService：同故事单写者、回合协调、版本校验、提交与纠正
    ├── SceneHost：场景推进、感知提案、结果协调、正文组织
    ├── PlotCoordinator：剧本约束、世界时间、剧情节点与条件推进
    ├── CharacterAgent：每个重要 NPC 的独立决策
    ├── ContextComposer：按调用目的与人物组装允许的信息
    ├── MemoryService：感知来源、个人记忆、回顾、检索、重建
    ├── SuggestionService：仅基于玩家可见内容的行动建议
    ├── ContentService：故事与人物编辑、导入导出
    └── WorldStoreManager：世界数据库、当前进度另存与读档切换
                         │
          TextTurnRunner：期限、取消、调用计量、格式校验
                         │
                 TextGenerator / Provider

WorldStore：每个世界的时间、剧情进度、事件、感知、正文、人物记忆、修订与运行状态
AppStore：用户、模型档案、剧本库、世界目录与另存任务状态
```

Agent 不直接写入权威故事，不任意读取数据库。StoryService 持有回合工作区与提交权；ContextComposer 提供受限输入；WorldStore 负责单个世界内的事务及所有权约束；WorldStoreManager 管理数据库生命周期与复制发布。

拟定代码落点：

```text
runtime/cmd/wia-app/          叙事应用入口：local / server
runtime/internal/story/      场景、人物、回合、上下文、记忆与纠正
runtime/internal/textturn/   通用文本调用执行器，不解释剧情
runtime/internal/apphost/    生命周期、任务池与模型档案
runtime/internal/appapi/     薄 HTTP 层与玩家/创作视图
runtime/internal/appstore/   应用库、世界库、迁移、事务与存档复制
runtime/internal/appauth/    真实用户、授权与会话
console/web/                 Vue 3 / TypeScript / Vite 玩家前端
desktop/                     Windows Electron 薄壳
```

以上是目标模块位置。代码留在 `runtime/` 的 Go internal 边界内，`textturn` 不导入 `story`，HTTP handler 不直接拥有生成任务或调用厂商 API。叙事服务直接管理世界并调用模型，模型客户端按本产品合同接入。

正式发布使用一个叙事后端入口和一套玩家前端。重构过程中用新世界回合替换外部游戏观察/动作链路，玩家工作台替换游戏连接控制台；完成替换后，旧 Gateway、Adapter 协议装配及其专用构建目标退出本产品。模型传输、身份键、适用的 SQLite 机制、检索工具及取消/计量基础代码按实际依赖复用，不以保留旧接口决定新业务模型。

后端采用模块化单体，Agent 是进程内调度的模型角色。StoryService、PlotCoordinator、ContextComposer 等首先实现为明确职责的普通代码，不预建跨产品运行框架、微服务或通用插件系统。

## 3. 三类职责

### 3.1 场景主 Agent

场景主 Agent 是一个逻辑主体，可按不同目的多次调用，并不意味着整个回合只请求一次模型。

| 职责 | 输出与边界 |
| --- | --- |
| 理解玩家输入 | 区分说话、观察、尝试与对结果的主张，识别交谈对象和相关人物 |
| 维护当前场景 | 地点、在场人物、已确立情境、正在发生的事及需交还玩家的选择 |
| 组织环境与背景人物 | 环境变化、合理外部事件、未提升为重要人物的路人表现 |
| 提议感知 | 根据场景提出谁看到或听到什么，内容可因接收者不同而不同 |
| 协调人物尝试 | 处理顺序、冲突、中断与行动后果，产生候选事件 |
| 推进情节 | 遵循剧本模式、固定事实和世界剧情条件，创造合理事件；允许玩家干预或不参与，重大主角选择交给玩家 |
| 输出正文 | 将玩家可见的已确定结果组织成一段完整叙事 |

主 Agent 可以协调“佣兵伸手拿钥匙”的结果，不能把老板的拒绝改成同意，不能代重要 NPC 选择背叛、承诺或主动透露秘密。需要改变立场或作出新选择时，重新向对应 NPC 提供新刺激并获取决策。

PlotCoordinator 是 StoryService 内的程序职责，负责时间、条件引用、节点状态与有界调度。场景主 Agent 提议事件内容及语义判断，程序负责版本、因果和状态提交。

主 Agent 的编排调用与最终叙述调用分开组装上下文。编排可以使用获准的作者隐情、事件和 NPC 意图；叙述仅使用玩家允许获知的投影及公开叙事约束。一个逻辑主体不共享无边界的模型会话记录。

最终叙述调用接收带 `actor_id`、人物名称、事件类型和叙事代称的玩家可见事件。玩家行动与 NPC 对白保持各自来源；私聊行动只投影交谈事实，不把耳语原文送入正文调用。正文人称、篇幅、描写密度和补充写作偏好按世界存档保存，默认分别为第二人称、标准篇幅和平衡描写。有限视角、玩家控制权、NPC 私密信息隔离和事件来源是不可覆盖的系统约束。

### 3.2 NPC Agent

重要 NPC 通过 `game_id + world_id + entity_id` 定位，拥有 `definition_id` 与定义版本、个人经历、信念与关系判断、当前关切和未完成约定。从模板新开一局不继承其他世界经历；手动另存复制当前世界截至保存时的完整经历。

每次决策读取自己的固定资料、允许获知的当前场景、相关记忆、近期经历和本轮新刺激，输出：

- 对外表达：对白、可观察表现与行动意图，或明确沉默。
- 角色状态提案：有来源的信念、关系判断、关切与约定更新。
- 必要的只读记忆检索请求，限定在该人物允许的来源中。

对白是人物说出的内容；说法的真假另行判断。行动意图是尝试；结果由场景协调。信念是主观认知；未来计划不属于已完成事实。角色状态记录保留简明结论及来源，不要求生成或存储隐藏推理链。

同一场景的重要 NPC 默认都有基于自身新感知作出反应的机会。沉默是有效决策，不能强制全员轮流发言。无新刺激且无需继续行动的人物，可沿用已明确的状态；任何实际获得的新经历均须保留，不能仅因没发言而丢弃。

NPC 无权读取其他人物私有记忆、替其他人物作决定，或直接修改全局事件。共享模型客户端不共享人物上下文。

### 3.3 程序层

程序层负责真实用户授权、参与者集合、事件顺序、感知访问范围、上下文来源、运行边界、版本、事务、保存和恢复。模型提出内容，程序校验结构与引用，并控制何时成为当前故事。

“记录中的人物是否在场”“来源是否属于此人”“引用是否存在”“版本是否过期”是确定性检查。场景记录本身的叙事合理性、“低声说话是否能被隔桌的人听到”“旁白是否改变承诺”属于模型语义质量，通过情境评测和用户纠正改进，允许少量偏差。字段过滤不能保证模型永不猜中秘密，提示词也不能替代访问控制。

## 4. 身份、世界与人物生命周期

### 4.1 标识与内容版本

| 标识 | 含义与生命周期 |
| --- | --- |
| `game_id` | 剧本的稳定身份；内容更新使用独立 revision |
| `world_id` | 一份持续推进的游玩进度及其数据库；新开一局或手动另存时生成，读取与正常游玩保持不变 |
| `entity_id` | 世界中的 NPC 实例；改名不变，复制世界时可保留，由完整身份键隔离 |
| `definition_id` | NPC 初始模板，按 game_id 与定义 revision 解析；同一模板可以产生多个独立实例 |
| `user_id` | 真实账户与世界所有者，独立于角色身份键 |

`game_id + world_id + entity_id` 是 NPC 的逻辑身份。场景主 Agent 按 `game_id + world_id` 管理整个世界，内部 purpose 区分编排和叙述。world_id 是叙事接口与存储统一使用的世界标识，NPC 实例统一使用 entity_id。

世界固定采用的剧本和人物定义版本，并保存恢复所需内容。模板更新不自动影响已有存档；作者明确应用修改时发布世界内修订。NPC 的后天经历与初始模板分开。

`turn_seq` 表示成功提交的交互进度；`context_epoch` 表示上下文与派生内容的失效版本。二者都不是可选择的历史存档。读档以 world_id 选择已存在世界的当前状态。

### 4.2 场景与人物

`SceneRevision` 记录当前地点、情境与重要参与者，另有每个接收者允许获知的场景投影。在场信息用于叙事因果和信息分发，不建立逐物件物理模拟。

每条候选事件绑定产生它的 run/attempt/stage、阶段内顺序、发生时的世界时间和场景快照。接收者资格按该事件的来源快照判断，不能用回合结束时的场景名单倒推整轮感知。

进入/离开作为有序场景变化处理：变化事件引用前置场景版本，产生后置版本，后续事件使用后置版本。进入者获得入场后的当前可见情境，不补获入场前的刺激；离开者保留先前经历，不继续获得离开后的场内谈话。进出动作本身按该变化的前后场景生成合理的可见投影，不能把观察该动作等同于获知全部前后历史。

通信与转述按独立来源事件授予感知，不要求接收者与原事件处于同一地点。直接引用已有阶段与 SceneRevision 表达顺序，不增加独立的全世界在场时间线。

重要 NPC 离场后保留身份与记忆，停止常规场内响应；世界剧情触发且需要该人物新决策时按需唤醒。其上下文仍限本人可知内容，结果与感知由世界回合统一提交。重返时获取当前可观察情境，不自动补齐离场期间的秘密。明确的转述、通信或后续观察可以形成新事件。完整的离场自主生活不在本阶段范围内。

普通路人由主 Agent 组织，可在事件中保留临时指称及可见表现，不启动逐人 Agent。用户通过“保留为角色”确认提升时，生成稳定身份，把已有可归属的资料和经历映射过去；新增背景单独标识为作者补充。不能由“曾经在场”推断获得整份历史。

模板定义、故事实例和主角身份分开。`User` 是真实账户，`PlayerPersona` 是该故事的主角资料，不能用主角名称做数据授权。角色改名不改变 ID。编辑模板不会自动改变已有故事。

### 4.3 剧本模式与世界剧情

剧本规模和剧情模式独立。GameDefinitionRevision 声明 `allowed_modes`、`default_mode` 及其约束配置；世界创建时采用 `open` 或 `guided` 并固定内容 revision。支持两种模式的剧本在开始前提供选择，已有世界的约束修改走显式内容修订及失效流程。

| 模式 | 世界运行合同 |
| --- | --- |
| open | 可包含多条世界剧情；玩家可选择参与、干预、忽略全部预设事件或发展自己的目标；世界按事实、人物目标和条件演进 |
| guided | 围绕作者主线目标、关键节点与替代路径组织事件，按明确的成功、失败或结束条件收束 |

流程型通常固定关键事实与目标，允许不同路径和成功、失败结局。严格指定结局是 guided 中的可选约束，必须同时说明玩家拒绝或目标不可达时的失败/结束处理，开始前告知自由度。不能用结局要求伪造主角同意、重要 NPC 决定或已发生事实。

剧本内容区分三类：固定事实与世界约束、人物未来计划、带触发条件和可能后果的剧情节点。尚未触发的计划不属于 StoryEvent，也不属于 NPC 已经历的记忆。固定事实可以作为世界或获准人物的初始知识；作者隐情仍保留其可见范围。

世界剧情可有多条，节点记录前置条件、时间条件、相关人物、可能后果、被干预或错过后的处理，以及所属剧情的结束条件。自然语言输入由内容整理调用生成结构化外壳和文本条件草稿，作者确认后发布；不执行剧本中的脚本，不要求普通玩家编辑条件表。

程序可以直接检查时间、已提交事件引用、节点依赖与版本；“是否消除了威胁”等语义条件由主 Agent 基于允许的证据提议。判断保留依据，不把字段存在等同于语义判断必然正确。

例如商队次日出发，埋伏未被发现且无人干预时可能遇袭。路线改变、预警或其他实际行动应重新判断条件，不能为保证原计划发生而任意补造等价袭击。玩家忽略事件不触发强制接取或反复引导；自然后果仍可发生。

开放型的一条剧情结束不自动结束整个世界。流程型只有在有效结束条件成立时完成，关键节点未满足不能仅因生成了结束语就标记成功。

### 4.4 游戏内时间与场外推进

每个世界保存独立 `WorldClock`。其世界内逻辑时间和剧本可读时间表达相对应，独立于现实时间、turn_seq 和 context_epoch。主 Agent 根据实际行动提议耗时，程序校验时间顺序与对应来源；不按模型耗时或消息条数直接换算剧情进度。

有时间成本的行动、等待和场景转换可以推进世界时间；普通对话按情境判定。设置、编辑界面、阅读历史、存档复制、模型等待、应用关闭或服务器闲置均不推进时间。重启或激活世界不按现实经过的时长补算事件。

推进前从当前世界状态检查可触发节点。对较长的等待或旅行，按有关事件的时间/依赖顺序处理：先解决会影响后续条件的事件，再判断后续事件，不在旧快照上一次判定所有未来结果。遇到需要玩家决定的事件时只推进到该时点，交还控制权。

世界事件推进受当前 run 的阶段与总期限限制，不运行无限后台循环。不需要逐个时间刻度模拟路人；事件涉及重要 NPC 的新选择时才按需调用对应 Agent。达到工作量边界时，可以在尚未开始下一个必要事件前停在一致时点并交还玩家；已开始的关键决策失败则按整轮失败处理，不能把尚未处理的时间段宣称为已完成。

场外事件的实际发生与接收者获知分别记录。目击者可立即获得感知，其他人物通过之后的观察、通信或转述获知。主 Agent 可以知道商队已经遇袭，玩家正文仍只叙述主角当时能够获知的迹象，不把后台剧情状态作为剧透下发。

世界时间、剧情节点状态和发生事件与本轮结果一起原子提交；失败或取消不留下单独推进的时钟。候选推进期间，按阶段发出的暂存感知仍只在当前工作区有效。

每次节点状态变化绑定节点版本、触发依据与结果事件，提交时检查预期版本。已提交的同一次变化不可再次执行；HTTP 重发、模型修复、恢复和读档均不得重复推进时间或重复触发同一结果。

## 5. 一次交互的因果流程

```text
玩家提交输入
    ↓
授权、幂等检查、故事预约、冻结配置与版本
    ↓
场景理解：输入意图、时间提案、剧本约束、参与者与各人感知
    ↓
程序校验并建立本轮暂存感知
    ↓
相关 NPC 基于同一阶段快照分别决策，可并行
    ↓
场景协调尝试、冲突与世界剧情条件，按时间顺序产生候选事件
    ↓
存在新刺激且需要回应 → 分发新感知 → 下一阶段相关 NPC 决策
    ↓
到达可叙述的稳定点或玩家选择点
    ↓
玩家可见投影 → 正文生成与格式/引用校验
    ↓
时间、剧情进度、事件、感知、正文、人物状态及完成态原子提交
    ↓
返回正文；异步整理回顾与生成行动建议
```

### 5.1 并行与顺序

同一阶段的 NPC 可以并行处理同一快照，各自输出相互独立的意图。不能把后完成的模型结果当成角色已经听过先完成者的对白；模型返回顺序不决定剧情顺序。

主 Agent 协调后产生新刺激，才进入下一阶段。例如老板说“我不知道”，佣兵听到后选择质疑；佣兵的质疑必须基于包含该对白的新感知。时间重叠或互相冲突的动作由协调步骤处理，不能直接拼接所有 NPC 的成功结果。

同一阶段发生场景变化时，协调器确定事件顺序及各事件适用的场景版本；并行 NPC 仍只使用各自调用开始时的快照。变化后的新感知通过后续决策阶段提供，不把新场景回填到已经完成的 NPC 请求。

本轮尚未最终提交的事件与感知仅在当前工作区有效。后续阶段可以读取这些已经通过阶段校验的暂存内容，必须带有 run/attempt/stage 来源；失败、取消或版本失效后整体丢弃，不进入长期记忆。

### 5.2 结束条件

默认最多三个 NPC 响应阶段，作为可调的活性保护起点；每阶段覆盖当时相关的重要 NPC，并不限制只能有一个 NPC。总期限、无新事件、重复意图和需要玩家决定均可触发结束。

达到阶段上限时，只叙述已经确定的结果，未完成尝试保留为尚在进行的情境并交还玩家。若关键冲突尚无法形成一致结果，则失败并保留输入供重试，不能把相互矛盾的意图都提交为事实。

关键 NPC 决策失败不能由主 Agent 悄悄代答；不存在“模型失败所以此人物选择沉默”的默认推断。完整回合失败时不提交部分剧情。辅助摘要、建议的失败适用独立规则。

### 5.3 典型知情差异

玩家向老板耳语，老板获得完整消息；佣兵只看到交谈迹象。老板公开否认时，佣兵获得“老板否认”的事件，并可产生怀疑；不会获得耳语原文。晚到者从当前场景开始，后来听到转述时保存转述者与来源类型。

该案例同时用于验证调用输入、阶段顺序、落盘记录与后续回应，不能只看最终正文是否像样。

## 6. 事件、感知、记忆与正文

四类数据必须有明确语义：

| 数据 | 含义 | 权威边界 |
| --- | --- | --- |
| StoryEvent | 已提交的发生事项，含发言、尝试、结果、场景变化 | 事实记录；“某人说 X”不等于 X 为真 |
| Perception | 某接收者获知的内容投影及来源 | 该人物能够回忆的输入，不默认包含原事件全文 |
| CharacterMemory | 人物对经历的整理、信念、关系判断与关切 | 主观与派生内容，带来源和版本 |
| StoryMessage | 玩家看到的输入与正式叙事 | 展示记录；玩家输入是表达或尝试，模型草稿不在其中 |

世界事件可以包含秘密，但 NPC 的检索候选必须从授权感知中构造。感知引用事件 ID 不授予读取原事件全部字段的权限。

协调输出以结构化外壳携带候选事件、结果与相应感知，正文根据玩家可见投影生成。提示职责要求正文尊重已协调的人物决定，新增关键决定应在协调阶段处理；程序检查结构与引用，不逐句证明正文与事件在语义上完全等价。

格式和引用有效的结果按正常流程提交。细节润色、偶发推断偏差或未被程序识别的语义矛盾由体验评估与纠正机制处理，不固定追加裁判调用，也不因抽象的“可能存在幻觉”阻止完成。持续改变人物决定或破坏关键剧情属于需要改进的质量问题。

## 7. 核心存储模型

| 记录 | 关键字段与约束 |
| --- | --- |
| User / Session | 账户、身份状态、会话和授权，不含主角心理资料 |
| UserPlayState | user_id、active_world_id、单调 active_revision；同一后端同一账户共享，位于应用库，不随世界另存复制 |
| ActivationRequest | 用户作用域的 request_key、请求 hash、预期活动版本、源/目标世界、操作状态和结果；位于应用库，支持幂等响应与切换恢复 |
| GameDefinitionRevision | game_id、世界设定、作者隐情、开场、角色模板、可见范围、允许/默认剧情模式及约束；不可变修订 |
| PlotDefinition | 所属定义 revision、剧情和节点 ID、固定约束、前置与时间条件、人物计划、可能后果、干预处理及结束条件 |
| World / PlayerPersona | user_id、game_id、world_id、存档名称、主角、剧情模式、有效内容修订、turn_seq、message_head、event_head、context_epoch |
| WorldClock / PlotProgress | 世界内时间、剧情及节点有效状态、已发生结果的来源、条件评估水位、发布版本；保存在本世界库 |
| CharacterInstance | entity_id、definition_id、定义修订、初始知识范围、在场状态关联 |
| SceneRevision | 地点、重要参与者、当前情境、来源与父修订；场景变化的前置/后置版本可追溯 |
| StoryRun / RunAttempt | request_key、请求 hash、输入 ID、attempt、状态、冻结快照与宿主 generation |
| RunStep | stage、actor、purpose、输入来源摘要、调用状态、暂存输出；非正式历史 |
| StoryEvent | 单调 seq、事件类型、行为者、内容、因果引用、run/attempt/stage、阶段内顺序、发生时间、来源场景版本；场景变化另含结果场景版本 |
| Perception | recipient、个人单调序号、source_event、来源场景/阶段引用、看到/听到/转述等来源类型、可见内容 |
| CharacterStateRevision | 本人信念、关系判断、关切与约定，来源、覆盖水位、basis epoch |
| DigestRevision | scope、recipient、连续覆盖范围、来源、版本与整理状态 |
| StoryMessage | 单调 seq、输入/正文类型、run、公开内容、支持事件引用 |
| Correction | 修改对象、范围、有效内容、来源、替代关系、epoch 与重建状态 |
| SuggestionSet | 最多三条、已提交正文 basis、内容与模型版本、有效状态 |
| ModelProfileRevision | 有权使用者、模型配置、受控凭据引用、不可变 revision |
| WorldDirectory / WorldCopyOperation | 应用库中的世界位置与发布状态，以及按 request_key 去重的另存任务、源世界版本和目标 world_id |

User、Session、UserPlayState、ActivationRequest、ModelProfileRevision、WorldDirectory 和 WorldCopyOperation 属于应用库；世界时间、剧情进度、人物、历史、记忆和纠正属于世界库。剧本库保存可供新建的定义，世界库保存本世界实际采用的定义及剧情约束。世界中的模型档案引用不包含凭据。

### 7.1 数据库布局

```text
<data-root>/story-app/
  app.db                                      账户、凭据元信息、剧本库、世界目录与另存任务
  worlds/<user_id>/<game_id>/<world_id>/
    world.db                                  此世界全部叙事数据及采用的设定内容
    assets/                                   此世界恢复需要的受控附件
  backups/                                    运维备份
```

一个 world_id 对应一个独立 SQLite 世界数据库。当前世界的每轮交互在该库内原子提交；手动另存在新位置建立新库。账号、会话和模型凭据留在应用级存储，不复制到存档。世界中可保存模型档案引用，读取时重新检查可用性与授权。

应用库中的剧本库用于创建世界；世界库保存当时实际采用的内容和修订，不依赖可变模板恢复。外部附件随世界复制，或使用保证引用存续的不可变内容存储；删除源世界不得破坏另存世界。

一个服务进程独占可写数据根，管理各世界连接。不同世界可并行调用模型，同世界遵守单写者；不支持多进程写同一世界库或共享网络文件系统部署。正常回合不需要跨应用库和世界库事务，列表所需进度缓存可从世界库校正。

### 7.2 所有权与引用

世界库元数据及故事记录绑定 `user_id + game_id + world_id`；人物记录增加 `entity_id`。查询、索引、复合外键、附件读取和导出使用相同所有权范围。应用目录定位后再次核对世界元数据，物理分库、UUID 和角色身份键均不代替授权。

必须具有：请求键唯一、事件/正文序号唯一、人物感知序号唯一、来源关联幂等、一个 input 最多一个成功回复、摘要 scope/revision 唯一、建议 basis 唯一等约束。人物感知水位、故事事件水位与正文水位各自独立，不能互相冒用。

模板、附件、用户输入和模型文本均不能拼接成文件路径。服务端生成文件 ID，校验大小与格式，不按正文中的路径或 URL 读取本机文件。新目录继承父目录的正常访问权限。

## 8. 上下文与可见范围

### 8.1 按目的构造输入

| Purpose | 允许来源 |
| --- | --- |
| host_orchestrate | 剧本模式、固定事实、相关世界剧情及条件、当前世界时间、作者授权的隐情、场景、相关事件和 NPC 意图，不默认全量读取所有私有记忆 |
| npc_decide | 本人定义与初始知识、本人感知、本人有效记忆/关切、本阶段新感知、对本人可见的场景 |
| host_narrate | 带行动者来源与叙事代称的玩家可见事件投影、主角、当前存档的正文表达设置、公开叙事约束、玩家回顾与有效剧情正文尾部；不读取失败或取消输入作为历史，私聊原文只保留为脱敏行动事实 |
| player_digest | 玩家可见的已提交内容、对应纠正及连续覆盖范围 |
| character_maintain | 本人已提交感知、本人状态、适用纠正与来源 |
| suggestions | 已提交玩家可见正文、主角、公开背景和有效玩家回顾 |
| content_draft | 用户明确选择的内容与作者补充，输出人物、剧情模式或条件约束草稿待确认 |

NPC 不读取整份玩家聊天记录、全局回顾或全知场景文本。NPC 的固定设定也区分自身知道的背景与仅作者知道的真相，不能把角色卡全部字段无条件放进角色脑中。未公开的世界剧情计划与结局条件不进入 NPC、玩家叙述和建议上下文；人物自己的计划可进入本人主观状态。主角在编辑器看到秘密不改变任何人物的知识状态。

过滤发生在候选来源选择之前，再做相关性排序、摘要与检索。相同规则覆盖当前输入投影、历史尾部、回顾、检索结果、场景快照、导出视图和缓存。不能先检索全库再要求模型忽略不该知道的部分。

界面消息与模型剧情历史采用不同读取合同。accepted、failed、cancelled、interrupted 的输入可供界面展示与恢复，不进入后续的历史尾部、NPC 来源、玩家回顾、检索、建议或剧情条件证据。当前 accepted 输入仅以“本轮待执行输入”注入对应 run 的编排步骤，再按暂存感知分发；显式重试时作为当前输入重新处理，不冒充此前已经说过或做过的事情。

历史中的玩家输入只有在对应回合成功提交后才可按已确定的事件解释，仍区分发言、尝试及实际结果。筛选覆盖所有上下文入口，不能仅以“数据库没有新增事件”证明失败输入未泄漏。

### 8.2 快照与来源完整性

一次 run 冻结 owner/game/world、账户 active_revision、基础 heads、context_epoch、内容与角色修订、剧本模式及剧情约束版本、世界时间与节点状态版本、初始场景、模型档案 revision、宿主 generation 与世界运行 generation。阶段快照额外记录 stage、暂存事件水位与引用的场景版本；每条事件和感知保留其实际来源快照。派生结果引用确切 basis，不能混用新旧版本；world_id 相同也不代表旧运行任务仍有提交权。

人物上下文由有效摘要覆盖的连续前缀、未覆盖感知尾部及相关检索组成。自动摘要尚未完成时，尾部补足最近发生的事。相同来源按 ID 去重，当前刺激不重复注入。

长期状态必须带来源或明确的作者设定标识。来源缺失、读取损坏或版本冲突返回可诊断错误，不能当作空历史继续。

### 8.3 检索与上下文边界

默认自动检索相关个人经历，NPC 可追加有界只读查询。首版可使用文字关键词检索，普通玩家无需选择检索实现或配置向量数据库。检索质量通过长程任务检验；后续替换索引不改变权限合同。

每次查询最长 256 字符，最多五个命中，每阶段最多两次追加查询，作为可配置实施起点。结果带感知/来源 ID、时间序号、文本和覆盖不足标识。无命中就是无命中；检索不写记忆、不制造历史。

最终序列化请求检查模型窗口与输出预留。可选检索按相关性裁减；必需身份、当前感知、关键纠正不能静默截断。先自动整理，仍无法容纳时返回可操作的整理或模型选择提示。暂不约束 token 成本不等于模型拥有无限上下文。

## 9. 记忆维护与统一纠正

### 9.1 原始经历与主观整理

本轮成功提交时，为实际获知新信息的每个重要 NPC 保存感知，包括保持沉默者。符合已确定结果的角色状态提案与正文同批提交；不能把落空的尝试写成完成的约定或事实。

摘要、压缩与较长程整理可以随后异步执行。下次调用使用有效摘要加完整尾部；后台整理失败不能让刚发生的经历消失。整理达到必需条件时在新 run 前有界完成，否则明确失败。

摘要覆盖必须是本 scope 的连续前缀，包含起止水位与来源。选择性检索条目不是连续摘要。玩家回顾、各 NPC 回顾分别维护，不能从全知摘要删几个字段就声称得到可靠的个人记忆。

人物的信念可与世界事实不一致。记忆整理保持“亲历、听说、推测、计划”的类型；关系判断与关切可由新经历改变，固定身份设定的修改经内容修订入口完成。

### 9.2 纠正对象

统一纠正入口要求指定对象与范围：世界事实/事件、人物设定、某接收者的感知、某人物的主观判断，或者错误的派生摘要。界面采用可理解的描述，后台保存精确引用。

更正派生摘要不自动更改其事实来源；更改人物信念不改世界事件。对事件进行修正时，更新受影响的有效投影；其是否被其他人物知道仍按原有合法来源和显式范围处理，不广播秘密。

纠正保留原文与来源，通过新修订表达当前采用的解释。它约束后续生成，不自动重演历史或撤销全部下游行为。手动另存复制当前有效状态；任意旧正文重写、成功回复重生成、未存档历史回滚与分支合并后置。

### 9.3 传播与重建

纠正通过故事单写者提交，递增 context_epoch，标记受影响的感知投影、人物状态、摘要、检索派生数据、建议、剧情条件评估和内容缓存失效。新调用只读取有效版本。改变未来计划或条件时重新评估尚未发生的节点，已提交事件保留历史，不因条件重算自动重演或撤销。

依赖范围必须可追溯；不能安全确定范围时采取保守失效。重建从原始已提交来源及有效纠正开始，记录 scope、水位、目标 epoch 和进度。每个批次发布前校验 basis，支持中断后继续；更新的纠正到达时，旧任务结果不再发布。

失效记忆若影响必需上下文，在重建完成前暂停相关新生成，并提供可理解的进度或错误。可用的未受影响内容仍可阅读。不能退回旧摘要继续写故事，不能借重建自动执行一遍旧 NPC 决策。

## 10. 默认功能与工作台

第一次使用的主路径是选择故事、确认主角、连接可用模型、进入开场。服务端已开放模型时省去玩家密钥配置。本地 BYOK 提供一次连接验证、明确错误和保存入口。用户不必为各 NPC 分配模型或选择记忆策略。

预置故事必须包含可直接游玩的开场、主角默认资料、重要人物及其初始知识划分、默认剧情模式、世界剧情与时间起点。多人协调、个人记忆、回顾与自动检索默认生效。支持多模式时在开始前用自然语言说明自由度供玩家选择，隐藏真相与结局答案不随选项泄露。模型和内部调度参数有完整默认值，高级配置不进入首次游玩必填流程。

输入框接受自然语言，可选 `addressee_id` 仅辅助指向人物，不作为排他参与名单。参与者与感知由故事情境确定。玩家不选择后台执行模式。

行动建议在正文提交后单独生成，最多三条，使用玩家允许来源。未选择建议不进入事件、记忆、索引或下一次 NPC 输入。点选只填输入框，修改与自由输入使用同一提交链路。

建议绑定 message_head、event_head、epoch 和内容版本；过期建议不能作为当前有效建议提交。失败时显示正文并保留自由输入，迟到结果不得覆盖正在编辑的文本。关闭建议后基础游玩正常。

普通游玩 API 仅输出玩家视图；有剧透提示的创作 API 可以读取该用户拥有的隐藏设定及人物结论。编辑入口不输出模型隐藏推理或 Provider 原始诊断。

## 11. 文本执行合同

核对基线中的 `model.TextGenerator` 已支持纯文本请求、响应及大小校验；`TextResponse` 当前只有 `Text`。`ModelDecision` 面向工具决策，仅含 ToolCalls/Control。本方案通过文本执行器与叙事私有类型表达场景/NPC 输出，不把正文伪装成游戏 ToolResult。

`TextTurnRunner` 接受 purpose、取消上下文、冻结模型档案、输入来源、期限与输出合同。负责真实调用、用量记录、UTF-8/长度校验、严格 JSON 解析和有限格式修复。未知关键字段、重复键、尾随内容、未知 actor/source ID 均应明确拒绝，不能猜测修复为事实。

现有 ValidateTextJSON 只负责 JSON 语法与 Unicode。复用时另外完成结构解析、重复键和关键字段检查，以及人物、来源和输出之间的引用校验，不把语法通过当成业务输出有效；这些是程序检查，不增加模型语义裁判。

叙事私有输出类型至少包括场景理解、接收者感知提案、NPC 意图、候选事件、人物状态更新和正文结果。结构化外壳管理来源、顺序与类型，内容仍可采用自然语言；无需为每种动作建立 DSL、物理属性或效果脚本。

模型供应商是否支持原生结构化输出由适配能力决定；纯文本 JSON 也必须走同一验证。格式错误最多修复一次，计入原阶段的期限与调用量。传输失败默认不自动重试；任何内部修复都不写正式故事。

Provider 返回实际用量时，通过窄扩展传递；否则记录估计量并明确标注。不能假定当前 `TextResponse` 已包含实际计费 token。NPC 使用 `AgentSessionKey(game_id, world_id, entity_id)`；user_id 负责授权，definition_id 与 revision 负责初始定义，个人感知范围由上下文服务另行约束。

## 12. 正文提交、幂等与恢复

### 12.1 接受输入

写请求包含 request_key、输入内容、可选 addressee_id、expected_active_revision 和 expected heads/epoch。按以下顺序执行：

1. 验证用户及故事权限。
2. 查找相同 request_key。请求 hash 相同则返回原 run；不同则冲突。此检查先于忙碌、当前版本和新模型配置检查。
3. 对新请求检查当前活动世界、expected_active_revision、expected heads/epoch、模型权限、配额与故事单写者预约；旧设备的写入不能隐式激活世界。
4. 冻结内容、场景与模型快照，持久化输入和 accepted run。
5. 后台 worker 执行本轮，生命周期独立于 HTTP 连接。

请求 hash 基于客户端规范化负载，不把后来解析出的模型 revision 纳入重发比较。同一请求在模型配置变化后重发仍返回原 run，不产生第二次输入和调用。

### 12.2 原子完成

输入作为已接受请求可先保存，但不自动认定玩家尝试已经成功。区分 run 接受前 `base_message_head`、保存输入后 `accepted_message_head` 与尚未推进的 `base_event_head`。

完成前校验 owner/game/world、账户活动世界与 active_revision、世界存续、预约、attempt、host generation、世界运行 generation、context_epoch、世界时间与剧情状态版本、预期 heads 及取消状态。在当前 world.db 的一个短事务中写入世界时间、剧情节点状态、本轮事件、感知、场景修订、人物状态、玩家正文、派生任务引用与 run completed，推进 turn_seq，并释放预约。

WorldStore 拥有这一事务，各叙事写入使用同一事务对象或等价的事务绑定接口。不得在其间调用自行打开连接并提交的旧 Memory.Append；同一数据库中的多个独立事务不构成整轮原子提交。

存储失败不展示正式回复或 completed；不能留下孤立记忆、半份事件或“正文未存但 NPC 记住了”的状态。候选数据即使为诊断暂存，也不属于可检索的历史。

### 12.3 单写者与重试

同一世界一次只接受一个改变当前状态的操作，覆盖生成、纠正、内容编辑、另存取样、读档切换与删除。跨世界可并发；模型请求期间不持有 SQLite 写事务。派生任务以 basis CAS 发布，不能绕过版本检查。

取消或失败允许显式重试同一未解决输入，创建新 attempt；一个 input 最多一个成功结果。新的后续输入被接受后，不能重试更早输入把回复插回历史。成功回合不通过 retry 再生成。

浏览器刷新只查询既有 run。超时响应不代表服务端未接受请求，客户端用同一 request_key 恢复，不另起输入。

### 12.4 取消、退出、重启和删除

取消与成功提交经过同一完成门，只有一个胜者。取消后的迟到模型结果不能发布。退出先关闭新工作与成功提交准入，再取消和排空任务；等待任务时不持有其完成所需的锁，必要清理事务仍可执行。

进程启动先取得数据根独占权并完成迁移，再将上一进程未终结的 run 标为 interrupted。已提交结果保留，未完成模型请求不自动重放，用户可以显式重试。外部模型可能已计费，应用不承诺跨崩溃的外部 exactly-once 调用。

删除故事或撤销访问权限必须取消相关工作并阻止迟到提交，摘要、建议或重建任务不能复活数据。读取失败与数据不存在分别报告，不能把损坏静默解释为空故事。

### 12.5 当前进度另存

正常持久化持续更新当前 world.db，不自动生成历史快照。手动“另存为新存档”仅接受源 world_id、名称、request_key 与预期版本，不接受历史 turn_seq/event_head 作为恢复目标。另存完成后仍停留在源世界。

另存流程：

1. 校验源世界所有权和幂等键；新请求还须验证源为当前活动世界及 expected_active_revision，登记稳定的目标 world_id 与复制任务。同键重发返回同一任务和目标，不重复另存。
2. 必需记忆重建未完成时，在暂停派生写入前结束本次请求并返回 memory_rebuilding，不等待重建。正在生成时可登记“本轮结束后保存”，指定该 run；其成功后在下一次修改前取得源世界预约。若失败、取消或切换世界，结束该保存请求并说明未完成，不静默保存另一份进度。
3. 在完整回合边界及世界协调门内重新核对活动版本、源版本和必需重建状态。仍有重建则释放预约并返回 memory_rebuilding；满足条件后才暂停派生写入，固定内容与模式版本、heads、epoch、世界时间、剧情触发进度及有效人物状态。禁止持有重建所需的锁、预约或写入禁令等待重建。已失败或取消的输入只保留界面恢复语义，不成为已完成剧情。
4. 通过数据库的一致性备份机制复制当前世界到未发布的目标目录，保留全部有效叙事数据及来源，复制所需附件。不得直接复制正在写入的数据库主文件并忽略其日志状态。
5. 在目标库事务中绑定新 world_id，保持 game_id、entity_id 与 definition_id；一致更新世界作用域字段、结构化来源引用和复合约束。世界内局部 ID 可保留，跨世界全局 ID 须重映射。校验来源完整性与定义版本。
6. 为目标初始化独立运行 generation；历史 run 仅作为历史保留，任务 lease、worker、锁和模型会话不作为可运行状态复制。未完成的可选派生工作根据目标有效来源重新登记，不携带源世界的执行权。
7. 校验目标库与附件，完成发布后将世界目录状态改为 ready。仅 ready 世界可以读取；成功响应前确保数据库和目录的完成状态可恢复。

应用库登记与世界数据库文件发布不是一个 SQL 事务。WorldCopyOperation 记录源版本、目标位置及发布阶段，启动恢复以此和目标元数据检查：完整目标幂等完成发布，未完成目标保持不可读并清理或重试。任何失败均保留源世界完整，不展示半份可用存档。

另存得到的是独立、可继续写入的世界。运维 backups 与玩家另存为新世界属于不同操作。

可选摘要和建议无需全部完成后才复制，目标按有效来源重新登记必要工作。源世界的复制冻结与删除保护在复制期间保持一致，所有失败路径释放保护；任务不能因队列替换而静默丢失。memory_rebuilding 的请求记录明确终态，用户在整理完成后重新发起保存，幂等重发仍返回原请求结果。

### 12.6 读取与继续

读取 B 是激活已有 world_id=B，保持其数据库和身份不变；之后所有交互持续更新 B。新开一局或主动另存时分配新的 world_id。

同一后端的每个真实用户最多有一个活动游玩世界，通过 UserPlayState 持久化，同账户所有设备共享。活动选择不是服务全局变量，也不属于单个浏览器页面。列表、正文读取、轮询及刷新只读取状态，不改变活动世界；新建世界后由显式激活动作进入，另存不切换。

激活接口携带 request_key 与 expected_active_revision。先授权和处理幂等重发，再检查活动版本；过期请求返回冲突并附当前活动元信息，不自动重新激活旧世界。有效请求的目标已经活动时返回当前状态，不递增版本、不取消任务。同键重复调用返回原操作结果及可供客户端核对的当前活动状态，不重放切换。

真正从 A 切换 B 时，使用用户级切换协调器串行处理：先验证 B，再关闭 A 的新生成与旧运行提交准入，结束或取消该用户在 A 的生成和相关派生工作，排空后发布 B 并递增 active_revision。取消与成功提交通过同一用户/世界协调边界确定先后；等待任务退出时不持有任务完成所需的锁。仅影响当前用户，不退役其他用户的模型或工作。

用户级活动选择和激活请求结果在应用库同一事务中发布，世界内容由各世界库保存，不通过跨库事务写入剧情。切换期间阻止该用户新生成准入；活动选择成功持久化后才报告切换成功。恢复时采用已发布的活动状态，旧进程工作按 interrupted 处理，未完成激活明确终止，不根据未完成请求自动重放切换。

任务始终持有创建时的 owner/game/world、active_revision、世界运行 generation 和数据库句柄，禁止提交时根据 UI 的“当前世界”重新选择数据库。前端通过状态轮询或事件获得切换结果，旧页面停止写入并提示已切换，旧响应不能覆盖新世界。生成与另存携带活动版本；服务端拒绝旧设备请求，不依赖按钮禁用保证正确性。

切换失败保留原世界数据并显示可恢复状态，不用模板覆盖损坏的 B。重新打开 B 时恢复其最新持久化内容、世界时间、剧情节点状态及未解决请求状态，不自动重放模型、不补算离线剧情。模型档案缺失或不可用时保留全部故事数据，提供连接选择入口。

界面明确当前存档名称和“进度自动保存到当前存档”。B 从第 10 轮推进到第 15 轮后，再次读取 B 就是第 15 轮；除非另有手动存档，否则第 10 轮只能作为历史阅读，不能恢复。客户端与服务端均不提供任意旧进度还原接口。

## 13. 宿主、模型档案与执行边界

AppHost 就绪表示存储、认证与执行池已就绪。某用户未配置模型是该用户的可恢复状态，不使整个服务不可用。

正式入口中，空 provider 或缺少可用真实模型返回 model_not_configured，不沿用旧工厂选择 Fake 的默认值来报告模型就绪。Fake 只在明确的测试或开发配置中启用，并在界面和诊断中标明，不能冒充真实模型验证。

每个故事选择有权使用的模型档案；同一档案默认供主 Agent、NPC 和辅助模块使用。个人凭据和管理员开放的共享档案分别授权。管理员共享模型受其设置的额度控制，不默认向全部账户开放。

模型档案更新经验证后发布新 revision。运行中的 run 保持原快照；新 run 使用新版本。明确禁用账户或撤销凭据时，取消相关调用并阻止未提交结果成功发布。

客户端缓存以 owner、profile_id、revision 为键，不按模型名字共享凭据。普通用户只能配置受控连接信息，不能提供服务器任意 env/file 引用。

默认边界是实施起点，需按实测调整，不是性能承诺：

| 项目 | 默认值或规则 |
| --- | --- |
| 主 run 并发 | 全局 4、每用户 1、每故事 1 |
| 模型调用并发 | 独立全局池 8，每 run 最多 4；NPC 可并行，辅助任务低优先级 |
| NPC 响应阶段 | 最多 3 个，有新刺激才追加；初始重要参与者不得因省调用被随意遗漏 |
| 追加 recall | 每角色每阶段最多 2 次只读查询，受总期限约束 |
| 格式修复 | 每步骤最多 1 次，修复失败则结束该步骤 |
| 单模型调用期限 | 60 秒；摘要/建议默认 20 秒 |
| 主 run 总期限 | 默认 300 秒，含排队、整理、调用和完成处理；压力测试后调整 |
| 落盘操作期限 | 独立短期限默认 5 秒，并受最终完成门控制 |
| 玩家输入/导入 | 默认 4,000 字符 / 1 MiB，字段分别校验 |
| 输出与上下文 | 按 purpose 配置；正文输出 2,048 估计 token 起步，按模型窗口校验 |
| 人物关切与建议 | 关切默认最多 8 条短文本，建议最多 3 条；原始经历保留 |

嵌套 NPC 任务不能把“主 run 并发四个”变成无限模型并发。取消、父期限和撤销传播到所有子调用。调用次数由参与者、阶段、检索和维护决定，不承诺每轮固定一到五次。

记录各 purpose 的调用次数、排队时长、输入输出估计量、实际用量（若提供）及 p50/p95 延迟。日志默认使用不透明 ID、版本与错误码，不记录密钥、正文、秘密或隐藏推理。

M1 即测量普通对话、私聊和插话的完整路径，分别记录总等待、各步骤耗时、并行程度、修复次数与失败率。300 秒是执行保护上限，不是可接受的游玩等待目标。小样本列出原始次数与耗时，避免把少量样本的分位数当作稳定结论；根据真实模型结果优化，不凭并行或调用次数推断体验已达标。

缓存后续优化必须区分模型客户端与内容结果：内容键包含 owner/game/world、recipient/purpose、可见来源与水位、内容 revision、epoch、模型和提示版本。私人记忆不跨人物或世界命中；带旧状态的决策不复用为新回合结果。另存不复用源世界的运行缓存，纠正和权限变化使相关缓存失效。

## 14. 桌面、网页与服务器

Windows Electron、本机浏览器和服务端响应式 Web 使用相同叙事后端与主要前端。Linux 服务器支持多个真实用户各自游玩，手机浏览器完成登录、阅读、输入、回顾、纠正和接续。

桌面壳负责启动、探测、关闭自己拥有的后端进程和窗口管理，不持有第二套故事逻辑。复用已有本机服务时验证身份，不能因退出桌面误杀外部进程。启动会话秘密通过受控通道传递，不出现在日志、URL 或普通命令行参数中。

Electron 开启隔离与沙箱，禁用页面 Node 能力，限制导航与 IPC。远程网页不获得本机文件、进程或任意命令桥接权限。

首版以轮询或状态事件展示 run 进度，正式正文完整提交后再出现。玩家看到“正在组织回应”等非剧透状态，不看到某 NPC 的秘密计划。流式草稿和任意成功回复重生成后置。

同一服务端数据可跨设备接续；独立本地与服务器之间通过显式导出、导入迁移。提供数据与密钥分别处理的备份恢复说明，不提供离线双向合并、多进程共享数据库或大规模托管容量承诺。

## 15. 认证、授权与内容边界

本地服务默认仅监听 loopback，使用启动交换建立本地会话并检查 Origin；服务器使用真实账户、成熟慢哈希口令方案、安全会话 cookie、CSRF 与反向代理来源配置。首版由管理员创建或邀请账户，不开放匿名注册。

每个读取、写入、轮询、附件、导出和创作入口都做 owner 授权。普通游玩视图与作者视图具有不同的返回字段，隐藏内容不得随页面初始化下发后仅用 CSS 隐藏。

模型凭据不回显、不进入导出包或诊断。服务端静态保存使用受控加密，主密钥与数据库分开配置和备份。此设计不代表运营者无法访问内容，也不得通过改变用户文件 ACL 实现。

服务器出站模型地址受管理员策略限制，检查 DNS、实际连接目标、重定向与私网地址。普通用户不能利用模型 URL 访问任意内网服务；管理员明确批准的本地模型有单独规则。Provider 工厂的文件与环境变量配置保持运维接口性质。

导入文本、角色对白、检索结果和模型输出都是内容，不执行其中的脚本、工具命令、SQL、系统指令或桌面 IPC。Markdown 使用安全渲染。模型提示中的职责约束与程序的授权/执行边界同时存在。

## 16. 编辑、导入与官方模块

支持 TXT/Markdown 背景、自有版本化故事 JSON，以及 `spec=chara_card_v2`、`spec_version=2.0` 的角色卡 JSON 文本子集。提取 `name`、`description`、`personality`、`scenario`、`first_mes`、`mes_example`，分别映射人物草稿、情境候选、开场候选和说话示例。

导入展示映射、遗漏项与知识范围草稿，确认后保存。信息范围采用产品默认推定并允许创作者修正，不要求普通玩家先逐字段标记才能开始。旧卡缺乏知情标注时不得宣称已准确还原所有秘密边界。

剧情文本整理使用 content_draft，提取固定事实、人物计划、关键节点、条件、干预路径及结束约束。作者预览并确认后，作为版本化剧本内容发布；系统不能因文中写有“商队遇袭”就把未来剧情直接记为已发生。无法确定的约束在草稿中标出供作者处理，普通玩家使用已准备好的剧本无需完成此流程。

`system_prompt`、`post_history_instructions`、宏和扩展字段不直接覆盖程序职责或执行行为。原 JSON 可在大小限制内作为不执行的附件保留。未知格式拒绝或按普通文本导入；PNG/CharX 容器与任意扩展附件后置。

自有内容包带格式版本、公开设定、隐藏内容范围、剧情模式与约束定义；世界存档另含当前时间和剧情进度。导出不含模型凭据、服务器会话或跨用户资源引用。导入创建新 owner 下的 ID，验证并重映射内部引用。

故事或人物的编辑通过版本化内容修订和统一失效路径发布。生成期间拒绝同时修改，或由用户先取消再修改，不能混用半轮设定。

官方模块通过普通代码装配，共用模型执行器、来源规则、版本和所有权，不建立任意插件执行环境：

| 模块 | 写入权限与失败语义 |
| --- | --- |
| 场景/NPC 协调 | 仅产生候选；失败则本轮不提交剧情 |
| 世界剧情推进 | 在同一世界回合内提出时间和节点变化；与事件一起提交，失败不留下孤立剧情进度 |
| 人物回顾与关切整理 | 仅发布符合 basis 的派生状态；来源保留，必需整理失败阻止不完整输入 |
| 行动建议 | 写建议集合；失败不影响正文与自由输入 |
| 导入/剧情约束/保留路人草稿 | 待用户确认后修改故事；生成失败保持原故事 |

## 17. API 与前端合同

| API | 合同 |
| --- | --- |
| `/api/v1/session` | 服务器登录、注销与当前会话；本地启动交换有独立入口 |
| `/api/v1/model-profiles` | 授权模型、连接验证和修订，凭据不回显 |
| `/api/v1/games` | game_id 对应的剧本库、模板版本、允许/默认模式、自由度说明、预览及受控导入；隐藏约束限作者视图 |
| `/api/v1/games/{game}/definitions` | definition_id 对应的 NPC 初始模板与版本 |
| `/api/v1/worlds` | 从选定剧本版本及其允许模式新开一局、按授权列出存档、元信息、删除与导出；当前时间按玩家可见范围呈现 |
| `/api/v1/worlds/{world}/save-as` | 手动另存活动世界当前进度，携带 expected_active_revision；幂等创建目标 world_id，返回任务及目标标识，不切换当前世界 |
| `/api/v1/world-copy-operations/{operation}` | 授权读取另存状态与失败原因，ready 前目标不可游玩 |
| `/api/v1/worlds/{world}/activate` | 以 request_key/expected_active_revision 显式切换账户的活动世界；重复当前目标不取消任务，过期请求不切回旧世界 |
| `/api/v1/active-world` | 只读当前账户的 active_world_id、active_revision 和切换状态，供同账户设备同步 |
| `/api/v1/worlds/{world}/entities` | entity_id 对应的角色实例、可见资料、定义引用、作者修订与路人提升 |
| `/api/v1/worlds/{world}/messages` | 玩家正文游标分页，历史阅读不提供历史恢复能力 |
| `/api/v1/worlds/{world}/agent-settings` | 更新当前世界的正文人称、篇幅、描写密度和补充写作偏好；携带 expected_context_epoch，当前回合运行时拒绝修改 |
| `/api/v1/worlds/{world}/runs` | 输入、可选交谈对象 entity_id、幂等键、expected_active_revision 及 expected heads/epoch/运行版本；返回 202/run_id |
| `/api/v1/worlds/{world}/runs/{run}` | 状态与非剧透阶段；取消/重试使用显式写接口 |
| `/api/v1/worlds/{world}/corrections` | 纠正对象、范围、版本与重建进度 |
| `/api/v1/worlds/{world}/memory` | 玩家回顾与来源；作者专用视图另行授权读取隐藏人物记录 |
| `/api/v1/worlds/{world}/suggestions` | 已生成建议及 basis；主动重生成要求幂等写请求 |

写接口要求 request_key 或 expected revision，创建、另存和激活必须可幂等重发。world_id 对应的 game_id 由已授权世界元数据解析，不信任客户端任意组合。读取分页和大小有界。前端以账户活动版本、world/head/epoch/run/运行版本校验响应，切换存档后旧请求不能覆盖新页面。

主要错误包括 unauthorized、forbidden、world_busy、version_conflict、idempotency_conflict、world_not_ready、save_failed、model_not_configured、text_generation_unsupported、context_needs_compaction、memory_rebuilding、generation_failed、storage_unavailable、suggestion_stale、quota_exceeded。界面呈现原因和可采取的操作，不要求玩家理解内部字段。

## 18. 实施工作单元

Phase12 是完整产品范围标识。内部工作单元由开发会话自行拆分和验证，按[开发执行指南](WIA_Phase12_开发执行指南.md)的 M1–M4 大阶段向用户交付体验验收，早期演示不代替完整交付。

首个示例为小型调查冒险，采用有限地点、少量重要 NPC、明确矛盾和关键真相；同一背景提供流程版与开放版。当前交付验证小剧本下两种模式和条件化世界剧情，大型开放世界内容与大范围长期演进后续扩展。

| 单元 | 交付内容 | 完成条件 |
| --- | --- | --- |
| 可开始并持续游玩的多人故事 | 主路径、AppHost/WorldStore、身份与定义、场景协调、两名 NPC、事件与个人感知、正文界面 | 无需配置 Agent 可进入场景，每个世界独立数据库，私聊与公开回应分别处理，持久化与刷新一致 |
| 持续人物与长期记忆 | 自动检索、个人回顾、关切、离场重返、近期尾部 | 多轮后约定延续，信息范围仍正确，摘要失败不丢近期经历 |
| 有世界剧情的两种玩法 | 模式与约束编辑、剧情草稿、时间与节点推进、场外事件投影 | 开放版允许不参与且事件按条件发展；流程版按节点及结局收束，两者均保留玩家决策 |
| 可检查和纠正的故事 | 来源、统一纠正、版本失效、可恢复重建 | 纠正后相关上下文与建议采用有效版本，秘密不被广播 |
| 可另存和读取的独立进度 | 当前世界完整复制、复制发布恢复、存档列表、读取切换与隔离 | 读取 B 持续更新 B，另存才创建新世界；未保存历史不可恢复，删除源存档不破坏副本 |
| 完整默认工作台 | 示例、模型引导、内容管理、导入、建议、保留路人、基础外观与响应式 UI | 新玩家无需技术配置完成连续游玩，编辑入口可发现且不打断正常阅读 |
| 服务器交付 | 真实登录与授权、模型档案、Linux 部署、手机与备份恢复 | 多用户隔离、跨设备接续、恢复演练通过 |
| Windows 桌面与整体验收 | 单次启动、本地会话、后端进程管理、完整质量与故障验证 | 普通用户可安装游玩，默认能力实际被使用，所有硬条件有证据 |

owner、game/world/entity 身份、定义版本、个人感知、世界分库和事务从首个工作单元存在。服务器工作单元不作为首次补授权的时机。核心运行链路按叙事产品重构，复用模型等基础设施时运行其受影响回归。

| A64 | 另存与必需重建竞争 | 冻结前及取得预约后检查重建状态；重建中返回 memory_rebuilding 并释放保护，不阻止重建发布后再等待它 |
| A65 | 失败输入进入后续上下文 | 界面可见的未完成输入不进入历史尾部、个人来源、回顾、检索、建议和条件证据；显式重试仅作为当前输入 |
| A66 | 未配置模型与输出校验 | 正式入口不隐式使用 Fake；JSON 语法有效但重复键、关键字段或引用非法的输出被业务校验拒绝 |
| A67 | 存储与任务机制复用 | 世界回合写入共享同一事务；必须完成的复制/重建任务不会被维护队列静默替换丢弃，取消与失败具有明确状态 |

## 20. 体验与竞品评估

至少准备三个不同题材，每个故事包含一名主角、两名重要 NPC 与若干路人，连续交互至少三十轮。关键情境至少重复三次，记录模型、参数、内容版本和波动，不以单次成功宣称稳定。

| ID | 评估内容 | 观察方式 |
| --- | --- | --- |
| Q01 | 新玩家能否开始 | 使用默认配置与现成故事，记录到首轮的操作数、用时、求助与放弃点；模型连接时间单列 |
| Q02 | 能力是否默认发生 | 不讲解技术开关，观察多人反应、记忆延续、回顾和建议是否自然被使用 |
| Q03 | 人物是否持续而有差异 | 帮助、威胁、约定及离场重返后，检查各自回应和态度变化 |
| Q04 | 信息差是否可信 | 耳语、旁观、晚到、转述、谎言和误解；同时检查合法输入与输出语义 |
| Q05 | 叙述是否忠于人物 | NPC 拒绝、隐瞒或提出条件后，旁白不改写其立场，不增添未经决策的承诺 |
| Q06 | 多人故事是否自然 | 无机械全员轮流发言、重复旁白或任务报告；必要时及时交还玩家 |
| Q07 | 纠正是否可发现且有效 | 用户找到错误来源并完成纠正，后续正文、记忆和建议遵循有效解释 |
| Q08 | 主角是否由玩家控制 | 不代作重大选择，不把行动建议或输入中的成功断言直接当事实 |
| Q09 | 等待与失败是否可理解 | 记录取消、重试、恢复和正文可读性；报告主流程及辅助调用 p50/p95 |
| Q10 | 长期使用是否可靠 | 重启、跨设备、摘要维护及备份恢复后，继续同一故事 |
| Q11 | 玩家是否理解存档 | 验证另存后留在 A、读取 B 后更新 B；玩家能识别当前存档，并理解未另存的旧进度不可读取 |
| Q12 | 开放型是否有剧情与自由 | 同一背景中参与、干预、忽略全部预设事件，均可合理推进；不以反复强推任务替代世界发展 |
| Q13 | 流程型是否尊重选择 | 验证不同路径、成功/失败和严格结局约束；拒绝关键行动时按规则处理，不伪造主角同意 |
| Q14 | 计划能否被真实改变 | 商队预警、改道或不干预产生符合证据的不同发展，避免为了命中预设节点随意改写事实 |
| Q15 | 时间与场外消息是否自然 | 对话耗时合理，等待遇到选择时交还控制权；通过迹象与转述得知场外变化，既有起伏又无全知泄漏 |
| Q16 | 跨设备切换是否可理解 | 电脑在 A 生成、手机读取 B 后，电脑显示切换结果；刷新 B 不打断任务，浏览历史不意外改动活动存档 |

每项质量指标报告通过数、总数、影响程度及典型偏差，不要求真实模型语义全项零错误。少量不破坏持续游玩的偏差可接受；频繁改变关键人物立场、反复破坏主线或导致无法继续的问题需要修复。硬授权、结构、版本和事务条件必须通过。真实模型的体验质量不能由 fake 测试替代，验收以连贯性、人物差异、选择反馈和可恢复性共同判断。

与 SillyTavern 的比较分为新手默认使用路径和合理配置后的叙事能力。采用相同模型、相近内容，披露准备工作与设置。对照可以验证 WIA 是否降低配置负担，也应尊重 SillyTavern 已有能力，不能以关闭对方功能证明领先。

内部消融分别检验个人记忆与知情范围是否带来可观察增益；后台 Agent 数量不作为产品优势证据。缓存优化前后使用同一组情境回归，不能以更快为由接受串记忆或旧版本结果。
